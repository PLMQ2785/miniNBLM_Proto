# 청킹 Preset 및 검색 알고리즘

## 1. 목적

관리자가 청킹 설정은 검증된 preset으로 선택하고 검색 알고리즘은 독립적으로
선택할 수 있게 한다. 청킹 변경만 전체 문서 재인덱싱을 유발하며, 검색 알고리즘
변경은 이미 유지 중인 DB 인덱스를 사용해 즉시 적용한다.

청크 크기와 오버랩의 단위는 token이 아니라 **문자 수**다. 현재 청커는 PDF의
각 페이지를 독립적으로 나누며 하나의 청크가 여러 페이지에 걸치지 않는다.

## 2. Preset 필드

| 필드 | 형식 | 초기 허용 범위 | 변경 영향 |
|---|---|---:|---|
| `key` | 영문·숫자·밑줄 | 고유값 | DB와 API에서 사용하는 안정 식별자 |
| `display_name` | 문자열 | 필수 | 관리자 UI 표시 |
| `chunk_size_chars` | 정수 | 200~3500 | 전체 문서 재인덱싱 |
| `chunk_overlap_chars` | 정수 | 0 이상, 청크 크기의 50% 이하 | 전체 문서 재인덱싱 |
| `top_k` | 정수 | 1~20 | 검색 실행 설정만 변경 가능 |

유사도 임계값은 실제 사용 문서 평가 데이터로 score 분포를 확인하기 전까지
preset 필드에 넣지 않는다. 임의 임계값은 관련 청크를 모두 제거할 수 있다.

## 3. 초기 Preset 5개

| Key | 용도 | 청크 크기 | 오버랩 | Top K | 최대 검색 문맥 |
|---|---|---:|---:|---:|---:|
| `fine_grained` | 짧은 정의, 수치, 핵심 용어 | 200 | 40 | 20 | 4000자 |
| `standard` | 짧은 절차와 간결한 문단 | 500 | 75 | 12 | 6000자 |
| `balanced` | 일반적인 강의자료의 기본값 | 1000 | 150 | 8 | 8000자 |
| `broad_context` | 문단 간 연결이 중요한 설명 | 2000 | 300 | 5 | 10000자 |
| `long_form` | 긴 서술형 내용과 사례 | 3500 | 500 | 4 | 14000자 |

기본 preset은 `balanced`다. 오버랩은 청크 크기의 약 14~20%로 설정했다.
최대 검색 문맥은 `chunk_size_chars * top_k`인
상한값이며 실제 페이지 길이나 검색 결과 수에 따라 작아질 수 있다.

## 4. 검색 알고리즘 4개

| Key | 방식 | 주요 용도 | 재인덱싱 |
|---|---|---|---|
| `dense` | BGE-M3 + pgvector cosine/HNSW | 표현이 다른 의미상 관련 문장 | 불필요 |
| `keyword` | PostgreSQL FTS `simple` config | 직접 등장하는 용어와 복합 키워드 | 불필요 |
| `substring` | pg_trgm similarity | 약어, 영문 용어와 부분 문자열 | 불필요 |
| `hybrid` | Dense + FTS + pg_trgm RRF | 일반적인 질문의 recall 보완 | 불필요 |

기본 알고리즘은 `dense`다. `chunks_embedding_hnsw`,
`chunks_content_fts_gin`, `chunks_content_trgm_gist`를 상시 유지한다. Hybrid는
각 검색에서 `top_k * 3` 후보를 가져온 뒤 RRF 상수 60으로 합쳐 최종 `top_k`를
선택한다.

## 5. 변경 및 재인덱싱 정책

Preset 변경은 전역 관리자 작업이다.

1. 관리자만 변경할 수 있다.
2. 변경 요청 시 대상 preset을 `pending` 상태로 기록한다.
3. 활성 preset과 대상 preset을 필드별로 비교해 변경 작업을 결정한다.
4. 청크 크기 또는 오버랩이 바뀌면 문서 재청킹과 재임베딩을 수행한다.
5. 검색 알고리즘은 별도 설정으로 즉시 변경하고 재인덱싱 작업을 만들지 않는다.
6. `top_k`는 현재 청킹 preset의 값을 사용한다.
7. 재인덱싱 동안 질문과 문서 변경 작업을 유지보수 상태로 차단한다.
8. `users`, `auth_sessions`, `documents`, 원본 PDF는 항상 보존한다.
9. 문서 재인덱싱 시 `document_pages`, `chunks`, embedding을 다시 생성한다.
10. 기존 대화는 chunk ID와 source 정보를 참조하므로 문서 재인덱싱 시
    `chat_sessions`와 `chat_messages`를 함께 정리한다.
11. 필요한 작업이 끝나면 대상 preset을 `active`로 전환한다.
12. 실패 문서는 실패 원인을 기록하고 관리자 화면에서 재시도할 수 있어야 한다.
13. 동시에 두 개의 preset 변경 작업을 실행할 수 없다.

전체 PostgreSQL database나 사용자 테이블을 drop하는 방식은 사용하지 않는다.

현재 built-in preset 5개는 모두 청크 크기 또는 오버랩이 다르므로 preset 간
전환 시 문서 재인덱싱이 필요하다. 알고리즘 전환은 어떤 preset에서도 문서
재처리 없이 적용한다.

## 6. DB/API 구현

현재 구현은 아래 정보를 PostgreSQL에 영속화한다.

- built-in preset의 안정적인 `key`와 설정값
- 현재 활성 preset key
- pending preset key
- built-in 검색 알고리즘 4개와 현재 활성 algorithm key
- 재인덱싱 작업 상태와 시작·종료 시각
- 문서가 마지막으로 인덱싱된 preset key와 index version
- 실패 문서 수와 오류 메시지

관리자 API는 preset 목록과 현재 상태 조회, preset 변경 시작, 작업 상태 조회,
실패 작업 재시도, 검색 알고리즘 즉시 변경을 제공한다. 일반 사용자 요청에는
HTTP 403을 반환한다. Web UI는 관리자에게만 설정 화면 진입 버튼을 표시하고
작업 중 진행률을 polling한다.

재인덱싱 작업은 현재 API 프로세스의 background task로 실행된다. 작업 상태는
DB에 저장되며 API 시작 시 `pending` 또는 `running` 작업을 찾아 진행률을
초기화하고 전체 문서를 처음부터 다시 처리한다. 별도 worker 확장, 재시도 횟수,
지수 backoff가 필요한 운영 환경에서는 영속 작업 큐를 추가해야 한다.

## 7. 완료 조건

- 항상 정확히 5개의 built-in preset이 제공된다.
- preset key는 중복되지 않고 기본 key가 반드시 존재한다.
- 모든 숫자 필드는 정의된 범위를 통과해야 한다.
- 모든 preset의 청크 크기는 200~3500자 범위에 있고 오버랩은 청크 크기의 20% 이하이다.
- `balanced` 기본값은 `1000/150`, `top_k=8`이다.
- 항상 정확히 4개의 built-in 검색 알고리즘이 제공된다.
- 기본 검색 알고리즘은 `dense`다.
- 네 알고리즘 모두 실제 문서에서 검색 결과를 반환한다.
- 구현되지 않은 검색 방식은 관리자 UI에서 선택할 수 없다.
- preset별 재인덱싱 필요 여부가 일관되게 판정된다.
- 검색 설정만 바뀌는 경우 문서 재인덱싱을 실행하지 않는다.
